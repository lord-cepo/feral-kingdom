# Feral Kingdom AI roadmap

The first implementation is the [headless match harness](HEADLESS_MATCH.md). It records and replays legal decisions using the normal rules. The [MCTS literature guide](MCTS_RESEARCH.md) covers the outcome-based baseline, tactical search, learned policy/value models, and the benchmarks for choosing among them.

Build a local opponent for human-versus-AI matches with prebuilt armies. Start with a one-action evaluator running the real rules, then add adversarial search that sees the opponent's response window. Tune and promote versions through headless tournaments and human playtests.

## What counts as strong

Define an average player as someone who knows the rules and has completed several matches but does not regularly play competitively. A proposed release target is **at least 70% wins against this cohort**, with a 95% confidence interval whose lower bound exceeds 50%. Count draws in the denominator and report wins, draws, and losses separately. This measures consistent strength across the cohort. A finite playtest cannot establish a win against every individual.

Use roughly 100 games across at least 20 players as an initial study. Balance seats and starting armies, limit repeated games per participant, and compute uncertainty by resampling players rather than treating all games as independent. Hold some army pairings back from tuning. Publish results by seat and army matchup alongside the overall result. Start with a provisional desktop target of 500 ms at the 95th percentile per AI decision, excluding presentation time, and measure it on the hardware the game will support.

## Research and algorithm choice

| Approach | Application to Feral Kingdom |
| --- | --- |
| One-action lookahead with a hand-written evaluation | Simulate each legal action and score its resulting position. Provides a playable baseline, a way to inspect evaluation errors, and move ordering for deeper search. It can still miss a delayed attack or a forced reply. |
| Iterative-deepening minimax with alpha-beta | First candidate for Hard difficulty when the battle state and transition rules are fully observable and deterministic. Good move ordering makes cutoffs more likely. Searching explicit opposing replies helps detect forced hero losses and moves that leave the opponent without a legal action. [Knuth and Moore, *An Analysis of Alpha-Beta Pruning*](https://doi.org/10.1016/0004-3702(75)90019-3) |
| Guided Monte Carlo tree search | Benchmark if broad deployment or choice trees prevent alpha-beta from reaching useful reply depth. UCT allocates more visits to promising branches while retaining exploration. Use the same evaluator at a bounded horizon and prioritize forcing moves, since a rare refutation can be missed under a short budget. Compare against alpha-beta at equal wall time. [Kocsis and Szepesvári, *Bandit Based Monte-Carlo Planning*](https://aima.eecs.berkeley.edu/~russell/classes/cs294/s11/readings/Kocsis%2BSzepesvari%3A2006.pdf) |
| Learned policy and value through self-play | Consider after measuring simulator throughput and where search loses. First train a policy to order moves using decisions from the strongest search version, then try a learned evaluator or AlphaZero-style training. Promote only on held-out games against previous agents and people. AlphaZero's results establish feasibility in the games studied. [Silver et al., *Mastering Chess and Shogi by Self-Play*](https://arxiv.org/abs/1712.01815) |

Audit battle visibility and randomness in the first milestone. Confirm whether both armies, reserves, and queued effects are public to the acting player. If a mode introduces hidden information, search from the player's observation and use a method that accounts for information sets. If rules introduce public random outcomes, model them as chance transitions with their actual probabilities. An explicit player/decision/chance interface follows the precedent in [OpenSpiel](https://arxiv.org/abs/1908.09453).

## Rules integration

**Existing callers.** [LocalMatchController](../scripts/ui/local_match_controller.gd) and [GuerraBoard](../scripts/board/board.gd) are the live match and presentation integration points. [RulesRunner](../scripts/runtime/rules_runner.gd) exposes command availability and submission, and manages captured effects and continuations. [Match](../scripts/runtime/match.gd) owns action spending and phase transitions. [PhraseExecution](../scripts/effects/phrase_execution.gd) and [TargetResolver](../scripts/effects/target_resolver.gd) own execution choices and legal references. Follow the current contracts in [M2 execution](M2_EXECUTION.md) and [selection](SELECTION.md).

**Proposed decision interface.** Expose the player who owns the current decision, its legal options, and a way to submit one option through the existing rules. Represent deployment, effect invocation, optional accept/decline, and pending subject or target choices. Use stable unit/hex/property identities and deterministic option ordering. A shared Bash hex can yield two distinct UNIT options. Let the runner execute ALL phrases and resolve automatic steps. Preserve separate decisions when a cost or intervening trigger changes the later options. The initial baseline can roll out those continuations with a simple policy. Hard search should branch at meaningful choices, including choices owned by the non-active player.

**Simulation.** Run isolated matches using the authoritative rules and a disabled presentation gate. Audit code that reads the Match autoload before choosing the isolation boundary. [MatchSnapshot](../scripts/runtime/match_snapshot.gd) is a useful inventory of combat records and state, but its save gate requires an idle Action window. For a first simulator, replay an initial setup and decision transcript in an isolated headless instance. Profile replay before introducing faster in-memory branching. Fast branching must restore phase, action budgets, mutable unit state, queued attacks, grants, pending choices, captured events and continuation order, and RNG state if applicable. Where continuations contain callables, reconstruct them by replay or represent them as explicit state before attempting to copy them. Share immutable authored definitions where safe.

**Live match.** The local controller schedules the AI only for decisions it owns. Revalidate the result against the current match and decision revision before submission. Use the same action payment path as the human controller. Feed the bot side's trigger acknowledgement into the existing two-player gate once presentation allows it. Human acknowledgement and the animation sequence continue through the existing board flow. Cancel obsolete searches on reset, exit, or decision changes. Keep simulation off the live match, and keep frame pacing measurable during AI turns.

## What the evaluator should see

Use a symmetric score measured from one fixed player's perspective. Give authoritative terminal wins and losses priority over all positional terms, including the settled loss for having no legal deployment or action and the hero sacrifice/rescue timing. Normalize features before tuning. Begin with these terms and test each against held-out positions.

- **Hero safety.** Score credible incoming lethal threats, safe escape hexes, and the next legal actions available to save the hero. A queued Fire may survive its source's defeat and still miss if the original victim moves. Evaluate it through combat resolution.
- **Ready force and tempo.** Value current life, unit usefulness, available actions, activity, Stun, and likely recovery. Penalize leaving the player close to having no legal action. Evaluate an army's ability to act after the correct Start recovery and owner End activation.
- **Control and deployment.** Favor regions that open useful vacant deployment tiles and can be held. Query ControlResolver for actual control and the derived combat bonus. Evaluate reserves by realistic deployment access.
- **Threats and exchanges.** Value favorable Bash, shielding, suppression and threats to useful targets. Let real simulation settle Titanium, Obsidian, temporary counter consumption, area damage to either side, and bomb chains. Avoid counting a queued attack as both guaranteed damage and positional pressure.
- **Synergy.** Use live contributions and legal ability access to value hero adjacency, buffs, and unit combinations. Review recurring losses before adding card-specific weights.

## Implementation milestones

1. **Build a rules-driven headless harness.** Add deterministic setup, legal decisions, submission, and a trace recording setup, seed where applicable, rules version, acting player, options, chosen decision, and result. Run random-vs-random matches with a harness decision limit that reports timeouts separately from game outcomes. Verify live/headless parity on replay fixtures and state independence between simulations.
2. **Ship a playable baseline.** Add a local Human vs AI option and one-action lookahead. Keep random and greedy opponents as benchmark fixtures. Test both seats, optional choices, multi-action turns, human trigger acknowledgements and returning to the menu while the bot thinks. Log the main score terms for decisions so questionable moves can be reproduced.
3. **Search through opposing replies.** Add iterative deepening with a legal fallback from the last completed search. Use the decision owner's identity for maximize/minimize. Keep the same sign through consecutive actions or choices by that player. Measure depth in action or response windows as well as raw decision count. Where the horizon cuts off just before queued combat or a forced choice, allow bounded tactical extensions. Order previous best moves, likely lethal threats and defenses first. Keep a fixed-node mode for reproducible analysis and a time budget for play.
4. **Optimize where measured.** Track legal options per node, simulated transitions per second, time in cloning/replay and effect resolution, and effective opposing reply depth. Add a transposition table only after proving a position key includes all future-relevant state, including phase, decision owner, queued attack order, timed grants and pending choices. If the tree is still too broad, compare guided MCTS and progressively widen ranked options as visits grow. Keep forcing replies available early.
5. **Tune with tournaments and validate against humans.** Freeze each baseline. Run paired games with the same setup and swapped agent seats across mirror and asymmetric armies. Use both fixed compute budgets and live time budgets. Store losing positions and add them to a tactical suite. Use a separate held-out suite to decide promotion. Run the human study after the engine is stable and choose Hard difficulty based on human win rate and response time.
6. **Try learning if it addresses a measured weakness.** Export reproducible public observations, legal actions and search decisions. Measure whether learned ordering buys more reply depth at the same latency before committing to learned value or full self-play. Keep old checkpoints in the tournament pool to detect strategic regressions and use human playtests to confirm gains.

## Regression positions and reporting

- **Delayed combat.** Escape queued Fire with the original victim, preserve its captured identity, and find a defense against a bomb chain that threatens the hero. Exercise attacks that resolve after their source is defeated.
- **Choice ownership and identity.** Include optional triggers owned by the opponent, accept and decline with materially different outcomes, and two occupants of one Bash hex. Verify paid costs and action tokens are spent once.
- **Turn timing and legality.** Include free actions, multiple actions by one owner, Start Stun recovery, owner End activation, immovable temples, and regional control changes that alter deployment.
- **Terminal outcomes.** Include a settled no-action loss, a lethal hero attack, and a hero sacrifice whose followups can rescue it. Compare game outcomes to the authoritative runner.
- **Search integrity.** Replay the same trace twice and compare resulting state and decisions. Compare sibling branches in reverse order and check the original position for mutation. Compare alpha-beta against exhaustive minimax on small fixtures with consecutive decisions by one player.

For each candidate version report win/draw/loss counts by matchup and seat, tactical positions solved, invalid submissions, stalls or harness timeouts, p50/p95 think time, and achieved search depth. Require zero illegal submissions and unresolved rules stalls in the release suite. Evaluate strength at the same time budget so faster simulation and stronger decisions both count.

The first implementation milestone is the headless decision interface and replay harness. Future implementation should add GDScript contracts and update caller maps as the interfaces land.
